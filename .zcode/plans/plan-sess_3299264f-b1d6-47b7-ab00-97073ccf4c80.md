## Beep.DoitAll — Canonical Transaction & Ledger Engine

### The problem with the current shape
Today DoitAll (like Beep.OilandGas) has no single canonical "post a transaction" entry point. Each standard service (ECL, Impairment, Lease, CECL…) calls `AccountingBasisPostingService` directly, which inlines journal-entry creation. There's no aggregate enforcing balance, no transactional post, no source-document traceability, no period lock, and no plug-in seam for modules. The O&G `GLIntegrationService` was meant to be that seam but is a stub that silently returns fake IDs — a footgun.

### What "best practice" looks like (synthesized from Odoo, SAP, NetSuite, Square, Modern Treasury, Martin Fowler)
1. **Append-only** — posted transactions are immutable; corrections are counter-entries (`ReversalOf`), never edits/deletes.
2. **Balanced at the aggregate** — the transaction itself enforces `sum(debits) == sum(credits)`, not a service method.
3. **Source-document mandatory** — every transaction carries `{Type, Id}` so any GL line answers "which business document caused this?"
4. **Period-lock at the boundary** — the engine rejects posts to closed periods.
5. **Posting rules** — modules declare *how* their business events become journal entries, instead of each service calling the ledger ad hoc.
6. **One canonical entry point** — the `Ledger` domain service is the *only* path to the GL, for modules and external integrations alike.

### Architecture (layered, `Ledger` is the ONE class)

```
Modules (Sales, Inventory, HR, …) & external integrations
        │  raise an AccountingEvent  OR  post an explicit transaction
        ▼
┌──────────────────────────────────────────────────────────┐
│  Ledger (domain service — THE single canonical entry)     │
│   • PostAsync(AccountingTransaction)                      │
│   • PostEventAsync<T>(T businessEvent)  ← rule lookup     │
│   • ReverseAsync(transactionId, reason)                   │
│   • GetBalanceAsync(account, asOf, book)                  │
│   enforces: balance · account-active · period-open ·      │
│             source-document-present · immutability        │
└──────────────────────────────────────────────────────────┘
        │ uses                    │ consults
        ▼                         ▼
 PostingRuleRegistry        PeriodGuard / AccountResolver
  (DI-discovered rules)      (per-book account mapping)
```

- **Pluggable standards (IFRS/GAAP):** a standard = a `BookId` + its `IAccountResolver` + any divergent posting rules. Adding a third statutory book = register a new book + resolver. No engine change.
- **Modular:** each of your modules ships `IAccountingPostingRule<TEvent>` implementations. The registry finds them. Modules stop touching the GL schema directly.
- **Integration:** external systems call `Ledger.PostAsync(transaction)` — same invariants, same audit trail, no back door.

### New file structure (`Core/Ledger/`)

```
Beep.DoitAll/Core/Ledger/
├── AccountingTransaction.cs      ← aggregate root (header + legs); enforces balance + immutability
├── AccountingEntry.cs            ← one debit/credit leg (account, debit, credit, currency, dimensions)
├── SourceDocument.cs             ← value object { Type, Id, LineId } — mandatory traceability
├── EntryDimension.cs             ← flexible key/value leg dimension (CostCenter, Field, Well, Project…)
├── TransactionStatus.cs          ← Draft / Posted / Reversed
├── ILedger.cs                    ← the one canonical interface
├── Ledger.cs                     ← the implementation (the ONE class)
├── Posting/
│   ├── AccountingEvent.cs        ← base for business events (InvoiceApproved, PaymentReceived, …)
│   ├── IAccountingPostingRule.cs ← IAccountingPostingRule<TEvent> : Translate(event) → drafts
│   ├── PostingRuleRegistry.cs    ← resolves events → rules at runtime
│   └── AccountResolver.cs        ← wraps IAccountMappingService per BookId
├── Periods/
│   ├── AccountingPeriod.cs       ← entity (Open / Closing / Closed / Locked)
│   └── IPeriodGuard.cs           ← rejects posts to non-open periods
└── Balances/
    └── AccountBalanceSnapshot.cs ← optional read-model for fast reporting
```

### Key signatures

**The aggregate (enforces the golden rule itself, not the service):**
```csharp
public class AccountingTransaction
{
    public string Id { get; }
    public string TransactionNumber { get; }
    public DateTime Date { get; }
    public SourceDocument Source { get }     // mandatory, non-null
    public string BookId { get; }            // IFRS / GAAP / …
    public string CurrencyCode { get; }
    public TransactionStatus Status { get; private set; }
    public string? ReversalOf { get; }       // set on counter-entries
    public IReadOnlyList<AccountingEntry> Legs => _legs;

    public void AddLeg(string accountKey, decimal debit, decimal credit, …);
    public void Post();          // throws if |Σdebit − Σcredit| > tolerance, or any leg invalid
    public AccountingTransaction Reverse(string reason); // returns a NEW opposite transaction
}
```

**The ONE class:**
```csharp
public interface ILedger
{
    Task<ServiceResult<AccountingTransaction>> PostAsync(AccountingTransaction txn, string userId, CancellationToken ct = default);
    Task<ServiceResult<List<AccountingTransaction>>> PostEventAsync<TEvent>(TEvent businessEvent, string userId, CancellationToken ct = default) where TEvent : AccountingEvent;
    Task<ServiceResult<AccountingTransaction>> ReverseAsync(string transactionId, string reason, string userId, CancellationToken ct = default);
    Task<decimal> GetBalanceAsync(string accountKey, DateTime asOf, string? bookId = null, CancellationToken ct = default);
}
```

**The plug-in seam:**
```csharp
public interface IAccountingPostingRule<in TEvent> where TEvent : AccountingEvent
{
    /// <summary>Produce one or more balanced transaction drafts for this event + book.</summary>
    IReadOnlyList<AccountingTransaction> Translate(TEvent ev, AccountResolver resolver, string bookId);
}
```

### Hardening fixes vs. the O&G engine (these are the actual improvements)
1. **Transactional post** — `Ledger.PostAsync` persists header + all legs inside a single BeepDM `UnitofWork<T>` commit; a mid-post failure rolls back cleanly (today it orphans rows).
2. **Immutability enforced** — `Post()` flips status to `Posted`; the repository rejects any update/delete on a posted transaction. Corrections are reversals.
3. **Dimensions preserved** — `AccountingEntry` carries `CurrencyCode`, `FxRate`, and a flexible `Dimensions` dictionary (CostCenter, Field, Well, Project…) — not dropped at materialization like today's `GL_ENTRY`.
4. **Period lock at the boundary** — `Ledger.PostAsync` consults `IPeriodGuard` and rejects posts to closed/locked periods before writing anything.
5. **One balance formula** — `GetBalanceAsync` always respects `NORMAL_BALANCE` direction (today two code paths disagree).
6. **Source-document mandatory** — a transaction without a `SourceDocument` is rejected at `Post()`. No more untraceable GL lines.
7. **No stub footguns** — there is no `GLIntegrationService`-style stub returning fake IDs. The `Ledger` is the only path, and it always really posts.

### Migration / coexistence
- The **existing DoitAll standard services** (ECL, Impairment, Lease, CECL, Revenue, etc. from round 3) keep working unchanged — they currently call `AccountingBasisPostingService`, which I'll **refactor to delegate to `Ledger.PostAsync`** internally. So no churn to the 18 standard services.
- **New module code** should prefer raising events + posting rules, or calling `ILedger` directly for bespoke postings.
- The `ReportingService` (trial balance, P&L, balance sheet) stays reading posted entries — now it reads the canonical transaction store instead of reconstructing from lines.

### Scope of this change
- **Adds** the `Core/Ledger/` engine (aggregate, ledger, posting-rule system, period guard, source document, dimensions).
- **Adds** `AccountingPeriod` entity + `IPeriodGuard`.
- **Refactors** `AccountingBasisPostingService` to delegate to `ILedger` (keeps the 18 standard services working).
- **Registers** `ILedger` + `PostingRuleRegistry` in DI.
- **Adds** one example posting rule (e.g., `InvoiceApprovedPostingRule`) to demonstrate the pattern.
- Does NOT rewrite the 18 standard services, the 9 module services, or the reporting service — they keep their current contracts.

### Why this is the right "one class"
The user asked for one class that is the canonical transaction creator + ledger, that provides standards as a pluggable dimension and lets any module integrate. The `Ledger` domain service is exactly that: the single entry point, enforcing all double-entry invariants, standard-agnostic (book is a dimension), fed by plug-in posting rules, and open to external integrants on equal footing with internal modules.
