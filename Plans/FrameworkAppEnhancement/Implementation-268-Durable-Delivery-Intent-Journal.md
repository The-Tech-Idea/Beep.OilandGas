# Implementation 268 — Durable delivery intent journal

## Preparation and reviewer recovery

Save complete original preparation or independent decision intent before changing native delivery acceptance. Reuse the production data owner, Beep repository/transaction/audit patterns and explicit PRODUCTION migration type list. Canonical Data owns one validated delivery intent envelope and its append-only journal entity. A saved row preserves its original company/account/FIELD/ticket/source basis, UUID, full facts or decision, audit and revision. Exact unchanged retry may confirm the original row; competing commands, altered evidence or identity collisions must refuse.

The native journal stores commands separately from RUN_TICKET acceptance so saving a draft does not change measured quantities, receiving facts, native preparation/decision or workflow tasks. Read-back and current source/authority must close around an owned Serializable write. Recovery reads must return complete bounded company/account-owned evidence; malformed, duplicate, changed or excessive sets refuse explicitly. Missing metadata requires reviewed Beep Migration, never runtime schema creation or handwritten SQL.

## Canonical ownership and native persistence

TheTechIdea.Data owns RevenueDeliveryAcceptanceIntent and DELIVERY_ACCEPTANCE_INTENT. Exactly one preparation or independent decision is retained, including the full original source and original undecided preparation for a decision. The journal scope includes company, account, command kind, native ticket and original source revision. Complete row/body digests, unchanged ownership/audit, bounded command size and exact derived identities are required on every restore. Company, currency, measured unit and date evidence remain original; no conversion or inferred company defaults are introduced.

ProductionAccountingService owns saving and recovery through its existing PRODUCTION Beep repository. Saving requires an owned Serializable transaction, current authority and datasource identity, complete current delivery evidence before and after insertion, exact read-back and postcommit confirmation. The writer permits only insertion of its exact original row. Exact unchanged retry reads the original row without another insert; conflicting same-scope commands, foreign UUID collisions, malformed rows and uncertain outcomes refuse confirmation. Saving never changes RUN_TICKET measurements, acceptance facts, preparation/decision, process tasks or billing.

Single-entry and complete-set recovery revalidate current authority and read the full evidence twice. Complete-set reads refuse more than 32 entries or eight MiB of command characters rather than silently truncate. Native paging retains provider total/page/navigation evidence, exact membership and complete validated bodies, with at most 32 entries per page. Changed page/total, unavailable provider evidence, ambiguous identities or excessive bodies refuse. Commercial and delivery journals reuse the same production insertion policy and native page reader; no parallel persistence framework is added.

DELIVERY_ACCEPTANCE_INTENT is included in the explicit ProductionAccountingModuleSetup PRODUCTION entity list. Actual ClassCreator and ModuleSchemaBoundary checks verify canonical table/key/column metadata. The module declaration itself is source-reviewed; this focused composition does not compile the entire module setup or execute a migration. Runtime metadata must already match the reviewed Beep migration. No handwritten SQL, EF business migration or live schema application is introduced.
