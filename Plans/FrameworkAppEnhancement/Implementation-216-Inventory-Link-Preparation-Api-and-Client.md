# Implementation 216 — Inventory-link preparation API and typed client

## Procurement workflow delivered

The existing inventory controller and CompanyInventoryReads now expose revision-bound review and recording for a procurement preparer selecting an owned PO line and an owned inventory target. The typed accounting client consumes these endpoints. Preparation stores the retained proposal through the existing PurchaseOrderService owner; the current INVENTORY_ITEM_ID stays unchanged. Independent approval, reference application, stock movements and financial posting remain separate work.

GET `api/accounting/traditional/inventory/company/purchase-orders/{orderId}/lines/{lineId}/inventory-link-preparation/targets/{itemId}` captures the full owned purchase and target movement sources twice, requires active records, an explicit warehouse/location and exactly matching units, and closes the current authority and binding fence before returning the review. It is not a quantity-availability or approval assertion. A line already holding an unresolved preparation cannot obtain a replacement review through this path.

POST `api/accounting/traditional/inventory/company/purchase-orders/{orderId}/lines/{lineId}/inventory-link-preparation` accepts the shared Data submission containing the original command and review. It validates the decoded route, selected company and actor, original review/binding, canonical intent and reason. The existing native method reconstructs original line evidence for exact retained-intent retries, verifies the complete current source and target, and records only the preparation proof/audit in its owned Serializable Beep transaction. Exact retries add no writes; changing the original intent refuses. Unknown commit returns no confirmed result; the caller retains the original submission for reconciliation.

## Current company roles and grants

Both endpoints require authentication, current app-owned assigned standard roles, Procurement.View, Inventory.View and the explicit new Procurement.PrepareInventoryLink grant. IdentityServer remains authentication-only. CompanyModuleConnection supplies the current app RBAC scope, actor and PRODUCTION binding. Recording rechecks the entire sorted role/grant set, scope, actor and binding through the required native authority callback at its transaction/read/write/confirmation boundaries and again before returning. Foreign owned resources, changed binding/source and malformed intent are refused. No role/grant provisioning or permission assignment is performed.

The DTO lives beside existing shared contracts in TheTechIdea.Data. RequireResult verifies the canonical retained proof and exact command plus full original review; a successful HTTP response alone does not confirm the command. The typed client copies submissions/reviews/results, binds requests to its original company/account selection, encodes exact recorded IDs, and rejects late context changes, missing proof, mismatched intent or altered line/reference. There is no frontend database access, SQL or new EF business path. The existing Beep migration prerequisite for the bounded nullable proposal column remains unchanged and unprovisioned here.
