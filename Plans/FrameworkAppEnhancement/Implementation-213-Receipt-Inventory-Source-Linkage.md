# Implementation 213 — Recorded receipt-to-inventory source linkage

## Linked company data workflow

The existing PO_LINE_ITEM now has one optional recorded INVENTORY_ITEM_ID, owned by TheTechIdea.Data and bounded to 128 characters. Procurement source detail displays that recorded reference. It is not inferred from item descriptions, supplier identity, current field or a selected warehouse. Existing lines without a reference remain unlinked.

PurchaseReceiptInventoryReview is a shared Data source graph containing the complete canonical PO/header/line/receipt review, owned inventory item/movement review, selected receipt, PRODUCTION binding and content revision. It verifies the receipt belongs to the owned PO line and that the line's exact recorded inventory ID identifies the owned active item. Order, line, receipt and item must all be active. The current receiver decision must pass the existing canonical decision-proof verifier, including physical quantities, original evidence and receiver audit. PO line, physical receipt, receiver command and item must have the same exact recorded unit; no unit conversion or default is substituted. Warehouse and location must be recorded. Unknown on-hand quantity remains unknown; no stock or financial eligibility is manufactured from it.

The existing CompanyInventoryReads owner captures the entire linked source graph twice and closes the original company/account/PRODUCTION binding/full assigned-role/grant context. Both Procurement.View and Inventory.View are independently required with current standard app roles. Both captures must have the same full graph revision. Changing the stored line reference, inventory location/content, receipt proof or other source evidence refuses the review. This read-only review does not require the receiver and reader to be different people; independent physical/financial command authority remains a separate planned decision.

The existing inventory controller adds GET api/accounting/traditional/inventory/company/purchase-orders/{orderId}/receipts/{receiptId}. Recorded route decoding and the typed client's exact ID escaping preserve original order and receipt identities. The client freezes selected company/account, verifies the canonical returned graph and rejects late context changes through the existing shared request fence. Existing PO, inventory, receipt and repository owners remain authoritative; no new data store or parallel model is added. This path creates no stock, journal, invoice, AP allocation or supplier-return effect.

## Beep schema and source proofs

The nullable PO-line reference uses Beep-reflected metadata in the existing ProductionAccounting module manifest, which already declares canonical PO_LINE_ITEM. Fresh procurement metadata now requires the reference column before PO-line repository access. Live PRODUCTION therefore requires a reviewed Beep MigrationManager upgrade before using these reads; no migration is executed here and no SQL or business EF path is added. Legacy rows are not automatically linked or adopted.

Unset references are omitted from raw line serialization and from the existing PO source digest's line evidence shape. Set references participate in the source digest, so stale reviews fail after a stored link changes. Existing unlinked source proof serialization retains its previous shape. The link is frozen into the existing UI line projection and displayed without granting inventory write authority. Link creation/reassignment, its independent review and audit/intention recovery remain open; the source review is not a provisioning or mutation path.
