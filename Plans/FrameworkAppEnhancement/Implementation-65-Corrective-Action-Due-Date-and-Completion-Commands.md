## Problem and resulting behavior

Recorded corrective-action reads were available, but due-date and completion methods still attempted generic mutations that the HSE policy correctly fenced. The completion method could alter a step before inserting status without one owned transaction. Its status identity used a timestamp, and it assigned the app user ID to a business-associate foreign key without a recorded mapping. Missing commit/readback/idempotency evidence could not establish durable success.

The actual service now delegates due-date and completion to a mandatory typed command contract owned by TheTechIdea.Data. ApiService implements the orchestration through the current Beep owners. Commands independently require current company HSE.ManageIncidents plus HSE.View, a current inherited FIELD write grant and current company FIELD entitlement at WRITE or above, the exact selected-FIELD review, unique canonical incident-response/project relationship, exact action sequence/key, recorded status and responsible project participant. IdentityServer remains authentication-only; existing app RBAC/standard ASP.NET role and permission tables remain authoritative.

Due-date changes persist an explicit requested UTC date on the exact open action. A missing or uninterpretable old due date can be replaced by that explicit fact; the old date is not inferred or converted through a default timezone. Completion records a current UTC actual-end date and an explicit approved COMPLETED status together. Notes are mandatory and bounded. Only recorded OPEN → COMPLETED is supported; completion recording does not approve or close the incident. Existing deadline interpretation continues to distinguish late completion.

## Canonical command and transaction boundary

- [ICompanyCorrectiveActionCommands](../../TheTechIdea.Data/OilGas/ICompanyCorrectiveActionCommands.cs) is the shared typed contract; no duplicate business DTO/entity or client-side database path is introduced. Existing public HSE/CA Models contracts retain the planned canonical Data consolidation work.
- [PPDMCompanyCorrectiveActionCommands](../../Beep.OilandGas.ApiService/Services/PPDMCompanyCorrectiveActionCommands.cs) reuses CompanyPPDMEvidenceReader and CompanyPPDMRowAccessPolicy for bounded exact relationship/reference/current-row evidence. Internal command evidence is validated by the existing row policy; ordinary generic HSE/PROJECT writes stay fenced, even for a manager. No generic mutation privilege is added to a FIELD grant or ambient transaction.
- The command revalidates actual account/company/database/FIELD/revision, independent app permission, inherited write-grant scope/version and current entitlement. FIELD write entitlement is checked again after relationship evidence. Exact incident-response/primary component/project snapshots and complete action/status/responsible snapshots refuse changes before transaction, mutation and confirmation. Revocation or relationship drift during the compound command refuses and rolls back when rollback remains possible.
- The [existing PPDMDataSourceTransaction](../../Beep.OilandGas.PPDM39/Core/PPDMDataSourceTransaction.cs) remains the transaction owner. Its new RequireOwned assertion reads the actual held transaction, physical connection and optionally required isolation. Corrective-action commands require actual Serializable isolation; weaker/unspecified/no-op/borrowed/unconfirmed provider evidence cannot authorize a write. No SQL, parallel transaction helper or EF business path is added. Configure/verify a capable actual Beep driver before production use; a test provider's explicit transaction evidence is not driver certification.
- Only private, one-use mutation permits for the exact prepared step update or status insert can pass the typed command. Complete original scalar/audit snapshots, prepared business snapshots, exact canonical keys/type/table/operation/actor, current relationships/references and owned Serializable transaction are checked. Insert/update audit values must come from the canonical common-column handler. The wrapper's reads are bounded to its exact prepared row and independently validated by the existing row policy.
- The updated step is cloned instead of mutating a returned evidence instance. Completion uses a generated unique status key and explicit PPDM GUID/row-effective timestamp before preparation, preserving exact-mutation verification under the actual common-column handler. App actor identity remains in ROW_CREATED_BY/ROW_CHANGED_BY; no business-associate identity is invented for DEFINED_BY_BA_ID.
- Before commit and after commit acknowledgment, the exact complete saved step/status/audit/responsible evidence is read back and checked. Provider OK with missing/wrong persisted data cannot establish success. Acknowledgment failure or post-commit disagreement reports an unconfirmed outcome for reconciliation; it is not reported as rollback unless rollback was actually confirmed.

The same explicit due date is a no-write retry under fresh authority/transaction/readback. A completed action is reused only for the same recorded completion notes, actor audit and app source; a different payload refuses reconciliation rather than creating a second completion or replacing evidence. A lost completion commit acknowledgment can be retried against that actual recorded outcome without reallocating its completion date or status. A new due-date/completion transaction is still required to establish provider capability and current command authority on these retries. These rules are recorded-effect reconciliation for the current operations, not a general cross-workflow durable intent/outbox service.
