# Implementation 118: Recorded maintenance inspection commands and screen

## Visible maintenance workflow

The existing canonical work-order detail now embeds one recorded inspection panel beside its FIELD components and workflow links. It loads inspection evidence independently: confirmed absence, loading and refusal/failure are distinct, and an inspection failure does not erase the header or become a successful empty list. The panel displays actual requirement sequence/category/text, reported jurisdiction/reference, requirement owner, result, inspector, recorded UTC inspection timestamp and rationale. Requirement text is HTML encoded.

An authorized command can add an explicitly entered requirement or record PASS, FAIL or NA against a reviewed unrecorded requirement. No result is selected by default; rationale is required. Existing recorded results have no overwrite action. Requirement creation does not certify readiness or completion, and an empty checklist does not pass. Supervisor acceptance and return-to-service remain separate gates. The existing page no longer retains its duplicate legacy checklist tab or one-click result method.

## Single existing service/API/client path

InspectionService is replaced in place. It uses typed Data-owned WORK_ORDER_INSPECTION through the existing company-bound Beep repository instead of nonexistent PROJECT_STEP_CONDITION columns. Hardcoded US/generic checklist arrays and SeedChecklistAsync are removed; the existing work-order transition owner no longer calls automatic seeding. Canonical parent/order workflow-state commands remain an independent unresolved mapping gap.

The existing inspection interface now carries the original FIELD and typed request/result. The existing work-order API/client adds explicit requirement creation and returns the recorded requirement/result for confirmation. Checklist transport no longer converts a null response to an empty successful list. RecordInspectionResultRequest requires original FIELD, inspection identity and source revision; its result default is empty. The existing AFE response projection was moved intact from Web into TheTechIdea.Data, preserving its namespace and removing the Web definition; the real typed client interface and Razor check exposed that dependency. No parallel AFE or inspection DTO/store/endpoint family was created.

The existing API company gateway supplies the inspection authority callback. It independently requires current original FIELD and WORK_ORDER READ/WRITE resource authority and rereads the canonical parent before and after authorization review, without demanding an inferred header workflow state. Actor/company/physical binding changes refuse through the existing WorkOrderDatabaseBinding. Current app-role/resource stores remain the authority; no role mapping or grant is invented from planner/technician duty names.

## Recorded command and outcome boundaries

Reads explicitly require the inspection table; unavailable Beep schema refuses instead of answering an empty list. Recorded rows must match original FIELD/order, active unique inspection identities/sequences and complete requirement/result evidence. AllConditionsPassed uses the existing single completion-evidence rule over validated actual records.

Requirement insertion and result recording require the existing owned serializable PPDMDataSourceTransaction. In-transaction reads check duplicate sequence or exact original inspection identity/revision. Current WRITE authority and original binding close before mutation and commit. Recording requires explicit result, rationale and authenticated inspector, preserves requirement provenance and refuses an already recorded result. The whole intended requirement/result is checked against in-transaction and post-commit readback, with fresh WRITE authority/binding before returning success. Corrections cannot silently overwrite an existing result; their reviewed reason/history command remains required.

WorkOrderInspectionState retains original company/account/FIELD/order intent during page lifetime. It freezes requirement inputs or the exact selected requirement revision/result/rationale, rejects wrong/late reviews, requires matching response and separate actual inspection reload, and preserves an unconfirmed command across company-away-and-back. Inputs failing validation do not start an uncertain result. The panel never retries automatically or clears uncertainty on arbitrary reload. This is not a durable receipt or cross-session reconciliation mechanism; a failed post-commit read remains uncertain.
