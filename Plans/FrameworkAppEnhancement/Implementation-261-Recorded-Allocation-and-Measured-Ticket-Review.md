# Implementation 261 — Recorded allocation and measured-ticket persona review

## Revenue persona workflow

The recorded revenue screen now offers Review allocation and measured ticket for transactions with explicit sales-contract and allocation references. It calls the typed company API and shows the exact ticket identity, FIELD, original timestamp, certification status, nullable net quantity, recorded volume unit and source/delivery revisions. Missing net quantity or units remain Unavailable. OPEN, unknown status and zero quantity do not produce a certified measured-quantity result. Reload clears previous evidence; company/account/FIELD changes and late responses cannot repopulate it. Loading and failure have explicit MudBlazor states.

The panel distinguishes the recorded certified measurement from delivery acceptance and independent approval. Price/unit compatibility, effective approved terms, delivery acceptance, invoicing and recognition remain separate reviews. It performs no billing calculation or mutation and does not change global FIELD selection.

## Existing native source chain

AllocationEngine writes RUN_TICKET.RUN_TICKET_ID into ALLOCATION_RESULT.ALLOCATION_REQUEST_ID. The new read uses that exact existing link from REVENUE_TRANSACTION.ALLOCATION_RESULT_ID. It requires one allocation by primary key and one run ticket by primary key with the original FIELD filter, verifies exact returned identities, active indicators and FIELD membership, and retains complete typed row evidence. It does not use ticket-number fallback, FirstOrDefault, or the undeclared ALLOCATION_REQUEST_ID column on RUN_TICKET used by the legacy revenue lookup.

The API verifies the current authenticated account, standard app roles, Accounting.View permission, company binding and FIELD read access through the existing context and sales-contract source owner. Repeated contract/source/native captures refuse changed quantity or source and datasource changes. The canonical digest binds the full contract/source, allocation and ticket. The SDK binds the response to the original account/company/window/transaction/source revision and rejects late company changes. This is repeated read consistency, not a transactional cross-module snapshot or proof of independent delivery approval.

The existing RUN_TICKET, ALLOCATION_RESULT, ALLOCATION_DETAIL and AllocationMethod definitions move from ProductionAccounting/Data into TheTechIdea.Data/OilGas, preserving their public namespaces, fields and enum values. Their partial compatibility properties move with them; ALLOCATION_RESULT.Details continues to use the same allocation-detail model. No competing business entity definition is introduced. The Method, Temperature and Purchaser C# aliases remain available but are excluded from JSON because their names collide with METHOD, TEMPERATURE and PURCHASER under web naming/case rules. Native fields remain the wire values. The new RevenueDeliverySourceReview is a canonical read contract over those types.

The three entity identities declare bounded 128-character Key metadata for Beep. Existing ProductionAccounting module entity registrations continue to reference the same public type names. No live schema provisioning, SQL or new EF business migration is executed. Focused metadata tests verify canonical assembly ownership, one Beep key and alias behavior. Persisted-data/provider and external binary-consumer acceptance remain required for the assembly move; current-source focused compilation does not prove those gates.
