# Implementation 47 — Composite facility grants

Date: 2026-10-05. Owners: CA-03/05/06; FG-01/10/11/12/20. Status: complete facility key propagation implemented with focused persistence/admission/policy/service/consumer/controller evidence. Historical administrative review, legal eligibility and integrated provider/release acceptance remain open.

## Problem and resulting behavior

Facility reads and checks already retained FACILITY_ID and FACILITY_TYPE, but direct grant/revoke requests and storage carried only an ID. The active verifier refused ambiguous direct facility assignments. The row policy supported only FIELD inheritance and represented grants as individual filters, which could not express a composite key as one conjunction. The administration screen consequently withheld direct facility assignments.

The existing [shared requests](../../TheTechIdea.Data/OilGas/AccessControlRequests.cs), [service contract](../../TheTechIdea.Data/OilGas/IAccessControlService.cs), [store contract](../../TheTechIdea.Data/OilGas/IUserAssetAccessStore.cs) and [grant entity](../../TheTechIdea.Data/OilGas/AppUserAssetAccess.cs) now retain FacilityType. All remain owned by TheTechIdea.Data. A FACILITY command requires both nonempty exact key parts, up to 128 characters without surrounding whitespace/control characters; other asset types refuse facility qualifiers. Optional contract parameters preserve the complete existing non-facility key shape without introducing alternate services, stores or unqualified facility fallback.

[RepositoryAssetAccessStore](../../Beep.OilandGas.ApiService/Services/RepositoryAssetAccessStore.cs) includes the facility qualifier in the deterministic facility grant key and stored identity checks. Two facilities sharing an ID but differing in type receive separate grants. Revocation filters and ordinal postchecks include the qualifier, preventing provider collations from revoking another type. Regrant preserves creation metadata and updates the same qualified grant. Existing current account/company Administrator, subject membership, organization assertion, database fingerprint and concurrency stamp checks remain mandatory.

## Admission and row authorization

[PPDMAssetGrantTargetVerifier](../../Beep.OilandGas.ApiService/Services/PPDMAssetGrantTargetVerifier.cs) verifies canonical composite metadata, active selected-company BUSINESS_ASSOCIATE and the exact active FACILITY_ID/FACILITY_TYPE record with CURRENT_OPERATOR equal to the selected company. It rejects missing, foreign, inactive, ambiguous or provider-mismatched records. It validates the cached datasource against the configured target before opening/reading and after reads, while retaining current authority/binding checks. Other reviewed target types use the same strengthened cached-target gate. The shared target validator reports a missing configuration registry explicitly rather than throwing a null-reference error. Existence/current-operator association does not prove legal ownership or JV eligibility.

[IPPDMRowAccessPolicy](../../TheTechIdea.Data/OilGas/IPPDMRowAccessPolicy.cs) now exposes GetReadConjunctionsAsync: OR between nonempty groups, AND within each group. The previous flat contract is removed; repository, facade, import/export gate and row-security diagnostics consumers move together. [CompanyPPDMRowAccessPolicy](../../Beep.OilandGas.ApiService/Services/CompanyPPDMRowAccessPolicy.cs) produces a two-filter direct facility group alongside separate inherited FIELD groups. Unqualified facility records never become direct predicates. Company constraints and caller filters remain mandatory within every SDK query.

The existing [PPDMGenericRepository](../../Beep.OilandGas.PPDM39/Core/PPDMGenericRepository.cs) sends each bounded group as an SDK filter list, rechecks the exact current group before querying, validates returned rows and all required equalities, deduplicates by the complete PPDM key and revalidates accumulated rows. Empty grant groups are refused. Authorization cannot combine an ID from one group with a facility type from another. No SQL, IN fragment or separate query owner is introduced. The existing 256-group limit remains; compound groups contain both facility key filters.

Mutation checks apply the same conjunctions and current access levels to existing/proposed rows. Generic mutations cannot change a facility key or its FIELD/company relationship, even if both old/new types are otherwise authorized. READ cannot mutate, WRITE cannot delete, and revocation during provider reads refuses the previously read rows.

## Active consumers

- [UserAssetAccessService](../../Beep.OilandGas.LifeCycle/Services/AccessControl/UserAssetAccessService.cs) forwards complete keys for grant/revoke, admits direct qualified facility reads and recomputes effective access from fresh subject grants. Its direct-only readback excludes inherited grant levels; inherited FIELD access remains independently available.
- The existing [AccessControlController](../../Beep.OilandGas.ApiService/Controllers/AccessControl/AccessControlController.cs) forwards FacilityType on both commands. Its local-account guard consumes the already-registered auth-owner account resolver delegate; standard ASP.NET Administrator guards remain, and services independently enforce current app-owned authority. It no longer depends directly on the static identity helper at this boundary. Full auth-owner/DI integration remains unverified.
- [Row-security diagnostics](../../Beep.OilandGas.ApiService/Services/CompanyRowLevelSecurityService.cs) and the shared RowFilterResult expose ReadConjunctions without flattening the key pair. JSON diagnostics retain one inner group for both facility filters, with company constraints separate and mandatory. FilterCount counts grant filters inside those groups.
- [AssetGrantAdministrationState](../../Beep.OilandGas.Web/Services/AssetGrantAdministrationState.cs) and the existing [page](../../Beep.OilandGas.Web/Pages/Admin/AccessControl/AssetAccess.razor) now permit direct facilities, require their type, retain it in confirmed row identities, show it in the grid/revocation confirmation and qualify grant/revoke readback. Same-ID facilities can coexist in the list. A changed/copied qualifier cannot become a revoke target; readback of another type cannot confirm a save.
- Existing SDK checks/shared JSON and actual hierarchy/path/Web selector consumers retain the complete direct facility key. No new client database access or local authorization branch is introduced.

## Repository upgrade and historical records

Actual EF tooling generated CompositeFacilityGrants migrations and snapshots for [SQL Server](../../Beep.OilandGas.Repository/Migrations/SqlServer/20261005132117_CompositeFacilityGrants.cs), [PostgreSQL](../../Beep.OilandGas.Repository/Migrations/PostgreSql/20261005132121_CompositeFacilityGrants.cs) and [Oracle](../../Beep.OilandGas.Repository/Migrations/Oracle/20261005132125_CompositeFacilityGrants.cs). Each Up adds only the nullable FacilityType column to the existing APP_USER_ASSET_ACCESS table, with no default value, handwritten SQL, guessed type, data rewrite or seed operation. All provider models match their generated snapshots. No live migration was applied. Business/module schemas remain Beep MigrationManager; this existing Identity/access repository remains EF-owned.

Historical unqualified facility rows remain recorded with their original flags/metadata. They cannot authorize facility reads/mutations, elevate qualified access or be silently renewed as a guessed facility type. A new qualified grant is admitted through the normal target verifier and has its own complete key. Qualified revocation does not rewrite the historical row. Dedicated administrator inventory/review/retirement of historical unqualified, inactive or inaccessible stored grants is still required; the ordinary administration page lists current PPDM-visible direct access, not all stored history. This is an explicit remaining task, not a completed migration/review workflow.
