## Persona handoff

The existing workflow inbox projection now distinguishes FIELD work from explicitly owned company accounting work. AP invoice and purchase-order tasks link to /accounting/processes/{encoded instance}, which exposes recorded assignments/history and the owned source workbench. The shared assigned-work panel used by the inbox and persona landing pages shows the scope and assigned role. Existing counts and filters still drill into the same admitted rows; no new task store, dashboard renderer or domain model is introduced.

UnifiedTask adds explicit ScopeKind and AssignedRole. The Data-owned WorkflowTaskRoute accepts only exact internal FIELD routes or company accounting routes for AP_INVOICE/PURCHASE_ORDER. Missing scope, unsupported source types and alternate/arbitrary routes refuse. Process identities encode once, preserving slashes, international text and literal percent sequences. PersonaTaskInboxState also checks the assigned role against the selected company's recorded role set and keeps its existing freeze, company/persona generation, count and failed-refresh checks. Deploy API and client contract changes together; old task projections without scope/role refuse rather than infer authority.

## Existing API boundaries

CompanyAccountingProcessReads extracts the detail controller's existing orchestration without duplicating ownership logic. Detail and inbox use the same current company/module/process/native AP/PO read boundary. Inbox calls supply the original selected company and actor; a mismatch refuses before process/native lookup. The existing helper still verifies explicit process ownership payload, current app roles/permissions, fixed bindings and two complete source/process captures.

WorkflowTasksController retains authoritative persona/workspace review and adds standard User.IsInRole checks. Company accounting candidates require the shared owned read, exact task/process/source/step parent identities, one pending or in-progress step, an in-progress process, the current step and matching required role. Explicit assignment must name the current actor or assigned role. FIELD work retains FIELD and entity READ resource checks. Closing review rechecks persona/company/roles, reads the task records again to refuse changed/deleted/ambiguous tasks, and rechecks process/source/assignment admission before publishing.

WorkflowTaskProcessAdmission is a relationship check after the owning read boundary; it does not establish company ownership or grant access by itself. Task records still lack explicit company ownership columns. Current company ownership derives from the exact process payload and native source read. No task/process ownership is backfilled and no rows are created. Preliminary process classification in the inbox remains on the existing bound process reader; full inbox integration and task producer ownership need their own verification. Separate reads/revisions are not an atomic task/process/native snapshot or a concurrency reservation.
