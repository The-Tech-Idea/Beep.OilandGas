# Implementation 135: Recorded process initiation source

## Source-to-process persona handoff

Implementation 134 established definition review and response/readback checks. Its generic start path checked resource permissions without reading the source record. The existing definition screen now requires an explicit recorded source review before enabling a start. The dialog shows actual source type/identity, original FIELD, recorded reference/description/status/actor where available, retrieval time and source-specific limits. Error feedback appears within the dialog. Source changes clear the review; overlapping, failed or late reviews cannot retain another source or company. Undefined source types remain explicitly unavailable on this screen instead of being linked generically. Existing source-specific HSE/compliance workflows are unchanged.

The actual accountant path reads JOURNAL_ENTRY and its recorded JOURNAL_ENTRY_LINE rows through the existing request-company-bound accounting owner. Empty recorded lines can be reviewed but do not establish posting readiness. It rejects unavailable headers/lines, incorrect identities/accounts and duplicate lines. The review includes all recorded header/line values in a stable line-ID-ordered content digest; amount, currency, status, provenance or other content changes invalidate the submitted revision. Journal data is company-bound; a direct journal-to-FIELD relationship is **unconfirmed** and the screen says so. No FIELD ownership, fiscal period, currency conversion, approval, balance or posting result is inferred.

The maintenance path reads the actual WORK_ORDER header/components through the existing FIELD-bound work-order owner. Source/table identity, original FIELD and component identities are checked; at least one actual component must establish the FIELD relationship. The digest captures recorded order identity/type/number/dates/instructions and ordered component references. Missing recorded lifecycle state and header actor stay unavailable. This review is not an inspection acceptance, maintenance completion, permit or return-to-service decision; it does not reinterpret legacy PROJECT-backed lifecycle commands.

## Existing API and shared Data boundary

The existing business-process API adds a read-only POST start-review operation using the same ProcessInstanceRequest and returns the new Data-owned ProcessStartSourceReview. POST here carries the review input without creating or changing persistent data. The contract validates original company/actor/FIELD/definition/source, hexadecimal revisions, supported source identity and UTC retrieval provenance. The existing Data request gains ExpectedSourceRevision. No duplicate journal/work-order entities, alternative persistence store or new database access is introduced in Web.

The endpoint resolves its existing bound operation service once. Each of two captures checks original company/FIELD, current definition revision/structure, independently authorized FIELD/source READ and recorded source evidence. Both captures must have identical digests. The start endpoint requires that recorded digest, calls the same reader again, and compares it before continuing its independent WRITE checks and existing writer. The typed Web client uses the original company snapshot, refuses empty reviews and validates returned original scope. The UI state requires the reviewed entity/revision before retaining an attempt; source invalidation also refuses later confirmation and preserves unresolved intent.

These captures are content-review checks, not atomic native concurrency, source-specific execution duty mapping or a durable command receipt. The writer can still race with a source/definition change after review. Native transaction/CAS, durable idempotency/reconciliation and configured initiation duties remain required. The page-session repeat block still disappears when the page is recreated. Standard app-owned ASP.NET roles and existing resource authority remain authoritative; no inferred role assignment or IdentityServer authorization was added.
