# Implementation 136: Company-owned procurement source workbench

## Procurement persona screen and recorded data

The new `/procurement` source workbench accepts an explicit supplier business-associate ID and shows recorded company-owned PO number/identity, supplier, status and expected delivery, with responsive labels, pagination and encoded header links. `/procurement/orders/{Id}` displays the actual header's dates, description, amount and recorded creator. The accounting landing links to this workbench. There was no existing buyer/receiver workbench to extend; these routes use one page/state/panel and the existing accounting client and PO API route.

A recorded PO amount is shown without a currency symbol or aggregation: the current header has no currency field. Line quantities/units, receipts, stock, invoice matching, payment and independent approval are explicitly unavailable on this header screen. The source list is not a KPI or all-company procurement dashboard. It is the active recorded orders returned for the entered supplier and explicit owning company. Unassigned legacy orders are outside that result; an empty result does not establish no historical orders or no demand.

The UI projection freezes displayed header fields and clears old content before reads, failed reload and supplier/company changes. Late responses cannot populate a changed selection. A company change clears supplier input and returns a detail page to the workbench instead of silently adopting the same local order ID in another company. Direct details use exact original company ownership and encoded identity. Existing assigned workflow tasks remain reachable; no fabricated PO approval/receipt action is offered. UI uses standard ASP.NET authorization and selected-company roles through User.IsInRole, plus Accounting.View metadata; the API independently rereads authority.

## Canonical ownership and Beep migration boundary

PURCHASE_ORDER, PO_LINE_ITEM and PO_RECEIPT were moved from their original Models source to TheTechIdea.Data under their existing namespaces. There are no second copies of these domain types. The existing PRODUCTION module's explicit manifest already declares all three typeof entries; rebuilding against the current Data owner exposes the updated PO type to Beep MigrationManager. The PO header adds nullable, bounded OWNER_TENANT_ID (64) and OWNER_COMPANY_BA_ID (128). Vendor BA is a separate supplier relationship and is never used to infer ownership.

The two columns intentionally remain nullable for additive migration and reviewed legacy reconciliation. No row is automatically assigned from the vendor, active FIELD, selected company or default connection. Native foreign keys into the app-owned RBAC store are not fabricated across database boundaries. Planning/applying the PRODUCTION Beep migration, checking target capabilities and reconciling old records remain required; no migration or ownership assignment was executed.

The existing asynchronous Accounting PurchaseOrderService now requires explicit CompanyScope on its operations, records ownership for its create path, scopes header/vendor queries with exact tenant/company filters and revalidates returned ownership. Vendor results require the recorded active indicator and exact supplier, with duplicate/null results refused. Shared Data PurchaseOrderOwnership checks are reused by service, typed client and UI state. Receipt reads require the owned header first and reject unavailable/foreign/ambiguous receipt membership. Receipt commands verify the exact requested line identity and its owned parent before writes. These source changes do not deliver maker/checker approval, transactional receipt/stock/ledger writes or command recovery.

The service refuses a missing request-bound PRODUCTION resolver instead of opening shared PPDM39. Before PO access it obtains fresh empty provider metadata and requires both owner columns. This prevents a pre-migration schema from silently producing an empty owned-order result. Runtime metadata proves column presence only; native type/constraint/capability verification still belongs to migration acceptance.

## Existing HTTP/client boundary

The existing PurchaseOrderController was unauthenticated and called the overlapping synchronous traditional owner. Its route now requires authentication and uses the canonical asynchronous owner. Read authority must match a freshly read selected-company app role through standard User.IsInRole and independently assigned Accounting.View permission; no new role or automatic grant was invented. The role may be a configured buyer role in the existing catalog. The API checks current company authority and PRODUCTION binding fingerprints before/after reads, and header content is reread before return. Fixed conflicts replace raw failure details.

The original create route now returns an explicit conflict without creating anything. Its legacy unreviewed body cannot create a company-less PO through the old owner. A reviewed creation contract, role/duty mapping, audit/transaction/idempotency and recorded readback must be implemented before enabling that action. The synchronous traditional service still exists for broader reconciliation; this client-facing controller no longer calls it. Internal canonical approval/receipt/close methods are not exposed by this slice and still require domain authority/concurrency work.

The existing AccountingServiceClient gains typed supplier/header reads and validates original company snapshots and Data ownership. The GET response is the canonical Data-owned header shape, replacing the old anonymous projection; repository consumers were inventoried and the new typed caller is updated. External client compatibility and full transport validation remain open. There is no client database access, handwritten SQL, business EF migration lane, custom CSS/JS, live provider writes or deployment.
